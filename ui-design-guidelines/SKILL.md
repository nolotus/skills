# UI 设计与信息密度规范

本规范用于指导前端组件开发时的视觉权重、信息排布与交互反馈设计。

## 界面信息密度

- **绝不重复展示**：同一面板、卡片或弹出层里，不要重复展示同一指标（例如总 token 既用大标题又用缩写行、输入/输出之和再单独占一行）。
- **摘要入口（如圆钮、侧栏图标）是次要信息**：
  - 不用主色数字徽章叠在图标上。
  - 用低打扰但“扫一眼能认”的图形（例如灰阶圆环弧线）代替。
  - 完整数字只放进点击后的面板中。
- **可辨度底线**：次要 ≠ 看不见。避免只靠细指针、1px 差或极低对比表达状态；在小尺寸（≈20px）下要在真实页面确认弧线/描边仍可读。
- **视觉权重**：只有展开层才用分区 + 完整数值；主操作（发送、上传）必须保持最强视觉权重。
- **紧凑展示**：拆成短主行 + 短副行（如主行 `7,071 / 1M · 1%`，副行 `↑6,876 ↓195` 且与积分同一行）。避免一行塞满括号与长标签；大上限用 `M`/`k`。
- **数值格式一致性**：一个视图内保持一致。明细用完整 `toLocaleString()`，窗口上限可用 `k/M` 缩写，绝不把同一总数写两遍。

## 交互完整性

所有的交互必须满足用户期待、有预期的闭环反应！

- **任何中间状态都必须可感知**：用户触发操作（点击、回车提交）后，界面必须立即给出反馈——进入 Loading、禁用重复触发、或提供取消入口；绝不允许「按下去几秒钟没有任何动静」。
- 耗时操作（分类、路由、建会话、网络请求）期间必须有 Loading 状态；超过约 1 秒的等待应可取消或至少可见进度。
- 操作完毕（如添加或保存）后必须自动关闭弹窗。
- 操作失败时必须要有明确的错误提示。
- **绝不要留下没有反馈的“半截子”交互。**

## 组件复用纪律

在实现交互（如确认弹窗、加载状态、按钮等）时，**必须首先搜索和利用代码库中已有的 UI 组件**（例如使用项目已有的 `ConfirmModal` 而非原生 `window.confirm`，使用已有的 `Button` 等），严禁重复造轮子或破坏整体 UI 风格的一致性。

## 边界

- 只提供 UI 设计与信息密度规范，不处理具体代码实现；实现流程走你所在项目的前端实现 skill/workflow
- 不覆盖纯逻辑修复、后端问题、数据流问题或单纯布局 Bug（如果不涉及重新设计）
- 不替代设计评审或产品决策；当需求本身不清晰时，应先回到 brainstorming / 设计阶段
