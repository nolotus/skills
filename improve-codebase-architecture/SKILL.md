# 改进代码库架构

识别架构摩擦，并提出“做深模块”的机会：把更多行为藏到更小、更清晰的接口后面。目标是提升 locality、leverage、可测试性和可导航性。

## 术语

尽量稳定地使用这些词：

- Module：任何同时有接口和实现的东西。
- Interface：调用方为了正确使用 module 必须知道的东西，包括不变量、失败模式、顺序要求和配置要求。
- Implementation：module 内部的代码。
- Depth：接口后面隐藏了多少行为。
- Seam：不改调用方原地代码，也能替换行为的位置。
- Adapter：挂在 seam 后面的具体实现。
- Locality：改动和 bug 能集中在少数地方。
- Leverage：调用方用更少认知拿到更多价值。

## 核心启发式

- 删除测试：假设把这个 module 删掉。如果复杂度直接消失，它大概率是浅的；如果相同复杂度会在很多调用方重新长出来，它就在发挥作用。
- 接口就是测试面。
- 一个 adapter 只能说明 seam 可能存在；两个 adapter 才说明这个 seam 真的成立。
- 文件小不等于架构好。比起把逻辑切成很多转发层，更优先追求职责集中。

## 过程

### 1. 探查

先读现有的代码结构、领域文档和架构说明。

然后看代码，找这些摩擦点：

- 理解一个概念必须在很多很小的 module 之间来回跳
- 接口几乎和后面的实现一样复杂
- 逻辑为了测试被拆开了，但真实 bug 出在调用方之间的编排
- seam 泄露了实现细节
- 现有接口让测试很难写

### 2. 列出候选项

用编号列表给出架构机会。每项都包含：

- 涉及哪些文件或 module
- 问题是什么
- 推荐的改动方向
- 对 locality、leverage 和测试性的收益
- 风险或迁移成本

除非用户明确要求，不要一上来就直接给很细的接口设计。

### 3. 深入其中一个候选项

当用户选定一个候选项后，再继续往下走：

- 这个做深后的 module 应该真正拥有哪个概念
- 哪些行为应该移到 seam 后面
- 哪些东西应该继续暴露在接口上
- 哪些测试会变得更容易或更有意义
- 当前命名是否真的对应这个概念

如果代码库里已经有 glossary、ADR 或架构规则，默认先遵守；只有在存在明确摩擦时才建议重开讨论。

## 输出风格

优先给发现，不要空泛表扬。好的建议应该具体到工程师可以判断值不值得做。

对每条建议，都说明：

- 现在的形状为什么造成摩擦
- 什么改动能让职责更集中
- 为什么这不是简单地“挪文件”，而是真的改善维护性
