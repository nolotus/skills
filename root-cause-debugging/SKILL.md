# 系统化根因调试法

随机修复浪费时间并制造新 bug。快速补丁掩盖底层问题。

**铁律：无根因调查不提修复。** 违反过程的字面就是违反过程的精神。

## 四阶段（每阶段完成才能进下一个）

1. **根因调查**：读完整错误信息和堆栈（含行号/文件/错误码）；稳定复现（不能复现就收集更多数据，不猜）；检查最近变更（git diff/commits/依赖/配置）；多组件系统在每个边界加诊断日志先定位哪层失败；追踪数据流到坏值的源头。

2. **模式分析**：找同仓库工作代码对比；完整读参考实现不 skim；列出工作与损坏的每个差异再小也别假设"不可能"。

3. **假设测试**：单一假设写下来（"我认为 X 是根因因为 Y"）；最小改动测试；一次一个变量；没过就提新假设不加补丁。

4. **实现修复**：先写失败测试；单一修复不做"顺便改进"；验证通过且无其他测试断裂。**3 次修复失败 → 质疑架构**，不试第4次：每次修复揭示新位置/新耦合 → 是架构问题不是假设错误，找人讨论而非继续打补丁。

## 红旗信号——发现自己在想这些就回阶段1

- "快速修复先试试，之后再查"
- "改 X 看看行不行"
- "加几个改动一起跑测试"
- "不写测试了手动验一下"
- "应该是 X，先修了再说"
- "一次修复"（已经试了 2+ 次）
- 每次修复在新位置暴露新问题

## 常见借口

| 借口 | 现实 |
|------|------|
| "问题简单不需要过程" | 简单问题也有根因，过程对简单 bug 很快 |
| "紧急没时间" | 系统化调试比乱猜重试更快 |
| "先试这个再查" | 第一次修复定调，从一开始就做对 |
| "几个修复合一起省时间" | 无法隔离哪个起效，还制造新 bug |

## Boundaries

- 聚焦系统化调试心法，不提供代码修复本身
- 不覆盖架构重设计（超过3次修复失败后转给 owner）
- 不替代具体工具（日志、性能分析、网络包）的学习
